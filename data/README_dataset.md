# Dataset README — Synthetic Data for University SOC FP Reduction Assistant

**Project:** C28 — AI Immersion (Semester 5)  
**Phase:** 1 of 3  
**Date:** 2026-09-03

---

## 1. Overview

This directory contains four synthetic CSV datasets generated by `generate_synthetic_data.py`. They simulate 30 days of alert activity across a university network, analyst dispositions, endpoint context, and confirmed incident labels.

All data is **fully synthetic** — generated programmatically with a fixed random seed (42). No real network data, real IP addresses, or real user identifiers are present.

---

## 2. Files

| File | Rows (approx.) | Description |
|---|---|---|
| `alerts.csv` | ~13,000 | IDS/SIEM alerts with metadata |
| `analyst_decisions.csv` | ~13,000+ | Analyst dispositions per alert |
| `endpoint_context.csv` | ~13,000 | Device/user context per alert |
| `incident_labels.csv` | ~13,000 | Confirmed incident ground truth |

All four files join on `alert_id`.

| Column | Type | Description |

### 3.2 analyst_decisions.csv

| Column | Type | Description |
|---|---|---|
| `alert_id` | string | FK → alerts.csv |
| `analyst_id` | string | ana_001 through ana_004 |
| `analyst_role` | enum | l1_analyst / soc_lead |
| `disposition` | enum | false_positive / true_positive / escalated |
| `time_spent_minutes` | int | Analyst time on this alert |

**Note on override_reason:** The field is nullable only because historical data was generated before the override-reason requirement was enforced. In the live system (app/), the API enforces a non-null override_reason for every override — see the failure case documentation in `tests/failure_cases.md`.

### 3.3 endpoint_context.csv

| Column | Type | Description |
|---|---|---|
| `alert_id` | string | FK → alerts.csv (or host_id for persistent context) |
| `device_type` | enum | laptop / smartphone / workstation / server / tablet / raspberry_pi / unknown |
| `os` | string | Operating system |
| `patch_status` | enum | fully_patched / partially_patched / unpatched / unknown |
| `is_managed_device` | bool or null | Whether device is in university MDM/inventory |
| `user_type` | enum | student / guest / faculty / lab_admin / unknown |
| `known_vuln_count` | int or null | Number of known CVEs on device (from vulnerability scanner) |

**Missing context design:** ~10% of records have `is_managed_device = null` and `known_vuln_count = null` and `os = unknown`. This is deliberate: it simulates guest devices that do not report to the university's asset management system. The recommendation engine must handle this gracefully (failure case F1).

## 4. Engineered Structures (Critical for Understanding the Dataset)

### 4.1 FP Cluster 1 — Guest DHCP Exhaustion

- **Volume:** ~300 additional alerts (10/day × 30 days)
- **Pattern:** `alert_type=DHCP_EXHAUSTION, source_segment=guest`
- **Ground truth:** 100% false positive
- **Endpoint context:** managed/unmanaged devices, patched, 0–1 known vulns
- **Purpose:** The dominant repetitive FP cluster that wastes the most analyst time. This is the cluster the assistant should learn to suppress efficiently (Phase 2) but currently recommends as FP with evidence (Phase 1).

### 4.2 FP Cluster 2 — Student/Guest DNS Flood

- **Volume:** ~210 additional alerts (~7/day × 30 days)
- **Pattern:** `alert_type=DNS_FLOOD, source_segment=student OR guest`
- **Ground truth:** ~100% false positive (captive portal, normal DNS behaviour)
- **Endpoint context:** managed devices, patched, 0 known vulns, dst_ip = internal DNS server (10.0.1.2)
- **Purpose:** The second major noise source. Critically, the **Novel TP** (Section 4.4) superficially matches this cluster.

### 4.3 FP Cluster 3 — Lab Port Scan

- **Volume:** ~90 additional alerts (~3/day × 30 days)
- **Pattern:** `alert_type=PORT_SCAN, source_segment=lab`
- **Ground truth:** ~100% false positive (legitimate research scanners)
- **Endpoint context:** managed workstations/servers, fully patched, 0 known vulns
- **Purpose:** Demonstrates that the same alert type (PORT_SCAN) can be FP in one segment (lab) and TP in another (admin). The recommendation engine must be segment-aware.

### 4.4 Novel TP — DNS Flood Masquerading as FP Cluster 2 ⚠️

**This is the critical test case for the "preserves novel threats" requirement.**

- **Volume:** 8 alerts (injected mid-to-late in the 30-day window)
- **Surface similarity to FP Cluster 2:**
  - Same `alert_type`: DNS_FLOOD
  - Same `source_segment`: guest
  - Same `signature_rule_triggered`: IDS-DNS-007
- **Distinguishing signals (absent in FP Cluster 2):**
  - `dst_ip`: external address (8.8.8.8) instead of internal DNS server (10.0.1.2)
  - `is_managed_device`: False (unregistered device)
  - `known_vuln_count`: 3–8 (high, vs 0 in FP Cluster 2)
  - `patch_status`: unpatched
  - `raw_score`: higher (0.5–0.8 vs 0.2–0.5 for FP cluster)
- **Ground truth:** true_positive, incident_category=dns_tunnelling
- **What the assistant MUST do:** Detect the anomaly signals, override the FP pattern match, output "ANOMALY_SIGNAL_DETECTED" with specific evidence: "Pattern matches DNS_FLOOD/guest FP cluster BUT dst_ip is external (not internal DNS server) AND known_vuln_count=5 (mean for FP cluster = 0) AND device is unmanaged."
- **What a naïve auto-suppressor would do (WRONG):** See DNS_FLOOD + guest = FP Cluster 2 → suppress. This is the attack vector the design explicitly guards against.

### 4.5 Conflict Cases (Failure Case F2)

10 PORT_SCAN/student alerts have two conflicting analyst decisions: one FP and one TP. These simulate the real-world phenomenon of analysts disagreeing on ambiguous alerts. The assistant must detect this pattern and refuse to suggest auto-suppression for it.

## 5. Generation Assumptions and Their Limitations

### 5.1 Stated Assumptions

| Assumption | Value | Justification |
|---|---|---|
| Base alert rate | 400/day | Calibrated to SANS 2023 SOC survey for ~10,000-user campus |
| Overall FP rate | 75% | Mid-conservative industry benchmark |
| FP cluster volume boost | ~600 extra alerts | To represent the repetitive daily noise pattern |
| Missing endpoint context rate | ~10% | Simulates BYOD/guest devices not in MDM |
| Novel TP count | 8 over 30 days | Rare by design; 1 in ~1,600 DNS_FLOOD alerts from guest segment |
| Conflict case count | 10 alerts | Enough to exceed conflict_threshold (default: 2 conflicts) |

### 5.2 Known Limitations of Synthetic vs Real Data

1. **Temporal correlation:** Real alerts cluster in time (an incident generates a cascade of alerts). Synthetic data has independent alert timestamps. Phase 2 should address temporal correlation in the learning model.

2. **IP address reuse:** Real networks have repeated IPs (same device generates repeated alerts). Synthetic IPs are random, underrepresenting the "repeat offender" pattern that analysts use in real triage.

3. **Alert causality:** Real alert streams have causal chains (a port scan precedes lateral movement). Synthetic alerts are independent events. The current rule-based engine does not model alert chains.

4. **Analyst behaviour realism:** Override reasons are randomly selected from a small pool. Real analysts write free-text reasons with significant variation. Phase 2 NLP processing of override reasons is out of scope for Phase 1.

5. **Patch/vuln data accuracy:** `known_vuln_count` is random within ranges. Real vulnerability data comes from scanners (Nessus, OpenVAS) with their own false-positive and coverage limitations.

6. **Time-of-day patterns:** Alert timestamps use weighted sampling for business hours, but do not model specific shift handovers, weekend vs weekday, or academic calendar effects (exam periods typically spike student-network anomalies).

## 6. How to Regenerate

```bash
python data/generate_synthetic_data.py
```
